**AI 대상 3공정 중 2개가 AI Agent다** (p.22):
> "입고·출하 공정에는 **RAG 기반 AI Agent**, 성분분석 공정에는 배합비율 최적화 제조AI(ML)를 적용하여
> 예측(ML) + 질의응답 기반 의사결정(AI Agent)이 결합된 지능형 제조AI 운영 체계를 구축"

**모델유형표** (p.22) — 배합 최적화AI 와 **동급으로 등재**되어 있다:

| 구분 | 적용모델 | 적용공정 | 적용목적 |
|---|---|---|---|
| RAG 기반 AI Agent | **LLM + Vector DB** | 입고/보관, 출하, 전사 | LOT 추적, 품질 이력 조회, 불량 원인 분석, 작업 지원 |
| 배합비율 최적화AI | XGBoost, Random Forest | 성분분석/배합 | 배합비 추천, 품질 예측, 불량 감소 |
| 설명가능AI | SHAP | 배합AI | 품질 영향 요인 분석 |

### 1.3 사업계획서는 기술 스택까지 이미 정해 놓았다 — 설계서가 이를 옮기지 않았다

**PDF p.20 「클라우드 SW 명세」** (원문 표 그대로):

| 품목 | 수량 | SPEC | 주요 SW | 주요역할 |
|---|---|---|---|---|
| AP 서버 | 1 | 4 vCPU / 8G MEM / 100G SSD | Nginx, Streamlit, FastAPI, Docker | Web/API 서버, 관리자서버, **AI Chat 서버** |
| DB서버 | 2 | 4 vCPU / 16GB / 300G SSD | PostgreSQL | 공정데이터, 환경데이터 등 |
| **Vector DB** | **1** | **4 vCPU / 16GB / 200G SSD** | **PostgreSQL, pgvector** | **SOP/매뉴얼/품질문서 등 임베딩 검색** |
| **AI 서버** | **1** | **8 vCPU / 16GB / 200G SSD** | **LangChain, LangGraph**, Prophet, Python | **AI Agent, RAG**, ML 예측분석/차트생성 |

**이 표는 이번 설계의 3대 결정을 이미 내려 놓았다:**

1. 벡터 저장소 = **`pgvector`** (별도 Chroma/FAISS 아님) → §3.5 가 이 결정을 따른다
2. 오케스트레이션 = **LangGraph** → §5 가 이 결정을 검증하고 따른다
3. **GPU 가 어느 서버에도 없다** (4~8 vCPU / 8~16GB) → §2 의 로컬 LLM 판정에 결정적

> **SF-TD2 §2.1 도 동일하다.** `ML-SRV-01` = AMD EPYC 8코어 / 32GB / SSD 256GB — **GPU 라인이 없다.**
> SF-TD2 §5 설비 조달 계획 총액 **24,500,000원**에 GPU 항목이 **한 줄도 없다.**

### 1.4 사업계획서가 규정한 보안 제약 — 이것이 §2 의 결론을 좌우한다

**PDF p.60 §9.2 산업보안조치 이행계획 5항** (원문):
> "데이터관리시스템 및 AI 모델 데이터는 내부 서버 또는 보안 클라우드에 저장하여 외부 유출 방지.
> **RAG 기반 AI Agent는 내부 데이터만 접근 가능한 폐쇄형 구조로 설계하고, 사용 로그를 기록·관리**"

이 문장은 두 가지를 계약으로 못박는다:
- **폐쇄형 구조** — Agent 가 사내 데이터 밖으로 나가지 않는다
- **사용 로그 기록·관리** — `FR-AG-05`(Agent 로그)는 "선택 기능"이 아니라 **보안 이행계획의 의무 항목**이다

### 1.6 반대 방향의 근거 — 온프레미스 결정도 사업계획서 안에 있다

**PDF p.55 §6.2 특이사항**:
> "**CLOUDE SERVR 이용이 아닌 자체 서버 요청 시 데이터 이관에 적극 협조함**"

즉 사업계획서의 **기본값은 클라우드**이고, **자체 서버는 도입기업이 요청할 수 있는 선택지**로 명시돼 있다.
SF-TD2 §6 은 그 선택지를 택한 것으로 읽을 수 있다. **둘 다 계약 위반은 아니다.**
다만 **예산(§4.7 클라우드 36,000천원)이 어느 쪽으로 집행되는지는 미정**이며,
이것을 확정하지 않으면 §2 의 어떤 안도 조달 근거를 갖지 못한다. → §8 제안 1번.

| **공정 데이터 외부 전송** | 없음 | **성분값·LOT·고객사·클레임이 전송됨** | 마스킹 후 전송. 문서 원문은 미전송 |
| **구축 리드타임** | 장 (모델 선정·벤치·튜닝) | 단 (수일) | 단~중 (게이트웨이 구축 포함) |

### 2.4 외부 API 비용 산정 (안 ②·③ 공통)

**전제 (보수적)**
- 사용자: SF-TD2 §2.2 클라이언트 20대 · NFR-P-04 동시 20명
- 질의량: **일 200건 × 월 22영업일 = 월 4,400건**
- 1건당 토큰: 시스템+룰 프롬프트 3,000(캐시 대상) + RAG 청크 5×400=2,000 + 대화이력 1,000 + 질문 100 = **입력 6,100** / **출력 500**

**Anthropic 1st-party 단가** (`claude-api` 스킬 캐시 2026-06-24 기준):

| 모델 | 입력 $/1M | 출력 $/1M | 월 원화 환산 (₩1,400/USD) |
|---|---|---|---|
| `claude-haiku-4-5` | $1.00 | $5.00 | 입력 $26.8 + 출력 $11.0 = **$37.8 ≈ 5.3만원** |
| `claude-sonnet-5` | $3.00 | $15.00 | 입력 $80.5 + 출력 $33.0 = **$113.5 ≈ 15.9만원** |
| `claude-opus-5` | $5.00 | $25.00 | 입력 $134.2 + 출력 $55.0 = **$189.2 ≈ 26.5만원** |

**프롬프트 캐싱 적용 시** (룰·스키마 3,000토큰 프리픽스를 캐시; 읽기 ~0.1배):
`claude-sonnet-5` 기준 입력이 6,100 → 실효 3,400 토큰 → **월 $78 ≈ 10.9만원 (약 31% 절감)**.
캐시는 **프리픽스 정확 일치**라 룰 프롬프트에 타임스탬프·요청ID를 넣으면 무효화된다 → §4.4 에 반영.

> **결론: 사업계획서 §4.7 클라우드 예산 1,000천원/월 이 이미 이 비용을 3.7~19배로 덮는다.**
> 안 ②·③ 의 API 과금은 **추가 예산을 요구하지 않는다.**
> 반대로 안 ① 은 **예산에 없는 GPU 구매**를 요구한다 (DEF-AR-005).

> ⚠ 위 단가는 Anthropic 1st-party 기준이며 OpenAI·Bedrock·Vertex 는 별도다. **계약 전 벤더 견적으로 재확인할 것.**
> 환율 ₩1,400 은 산정용 가정치다. 이 표의 목적은 **자릿수 판단**이지 정산 근거가 아니다.

### 2.5 `LLMProvider` 인터페이스 — 어느 안을 골라도 코드가 안 바뀌게

**설계 원칙**: 제공자에 종속된 코드는 **`src/agent/providers/` 한 디렉터리에만** 존재한다.
그래프 노드(§5)·룰 검증기(§4)·RAG 검색기(§3)는 아래 4개 포트만 안다.

```
포트 1  LLMProvider
        complete(messages, system, max_tokens, temperature, stop) -> Completion
        stream(...) -> Iterator[Delta]              # SSE 필수 (§7.4)
        count_tokens(text) -> int                   # 비용/컨텍스트 예산용
        capabilities -> {supports_streaming, supports_tools, max_context, name, model_id}

포트 2  EmbeddingProvider
        embed_documents(list[str]) -> list[vector]
        embed_query(str) -> vector
        dimension -> int                            # 색인과 질의가 반드시 같아야 함
        model_id -> str                             # doc_chunks.embed_model 에 기록

포트 3  Completion / Delta (반환 계약)
        text, finish_reason, usage{input, output, cached_input}, provider, model_id, latency_ms

포트 4  ProviderError (예외 계약)
        ProviderUnavailable   -> API 계약 503 "서비스 일시 중단"
        ProviderTimeout       -> 200 + answer_status="timeout"     (§7.5)
        ProviderNotConfigured -> 501 "미구현 — v1 범위 밖"          (§7.6)
```

**구현체 (설계상 3종 + 1종)**

| 구현체 | 대응 안 | 비고 |
|---|---|---|
| `OllamaProvider` | ① / ③(임베딩) | `OLLAMA_BASE_URL` · 모델명 설정 |
| `AnthropicProvider` | ② / ③(생성) | `claude-api` 스킬의 SDK 규약을 따른다. 스트리밍 기본 |
| `OpenAIProvider` | ② / ③(생성) | 동일 인터페이스 |
| **`NullProvider`** | **미설정 시 기본값** | 모든 호출에 `ProviderNotConfigured` → **API 는 501 을 계속 반환** |

> **`NullProvider` 가 이 설계의 안전장치다.**
> 제공자가 확정되지 않은 동안에도 코드는 머지되고, **런타임 동작은 지금과 100% 동일(501)** 하다.
> `api-contract.md` §8.10 을 깨지 않고 구현을 선행할 수 있다.

**선택 방식** — 환경변수 1개. **`system_settings` 에 넣지 않는다** (`db-schema.md` §6.8 경고: "비밀번호·API 키는 `system_settings` 에 저장하지 마라").

```
AGENT_LLM_PROVIDER   = null | ollama | anthropic | openai      (기본 null)
AGENT_EMBED_PROVIDER = null | ollama | anthropic | openai      (기본 null)
AGENT_LLM_MODEL      = <모델 ID>
AGENT_EMBED_MODEL    = <임베딩 모델 ID>
AGENT_LLM_TIMEOUT_S  = 30
```

`GET /api/v1/agents/health` (신규, §7.3)가 현재 제공자·모델·색인 상태를 그대로 노출한다.
**화면은 "AI 준비됨/미구성"을 이 응답으로만 판단한다.** 조용히 추측하지 않는다.

### 2.8 [G1] 송출 데이터 최소화 — 필드 단위 허용목록

> **이것이 이제 이 설계의 핵심 과제다.** ② 를 택한 이상, 나가는 것을 줄이는 일은
> 구조가 대신해 주지 않는다. **설계로 강제한다.**

#### 2.8.1 원칙 4가지

| # | 원칙 |
|---|---|
| P1 | **원문 행(row)을 프롬프트에 붙이지 않는다.** SQL 결과를 `SELECT *` 로 받아 그대로 직렬화하는 경로를 만들지 마라 |
| P2 | **허용목록(allowlist)이다. 차단목록이 아니다.** 목록에 없는 컬럼은 나가지 않는다. 새 컬럼이 생겨도 기본이 "차단"이다 |
| P3 | **식별자는 나가지 않는다. 별칭이 나간다.** `LOT-2026-001` → `LOT#1`, `SUP_A` → `공급사1`, 고객사명 → `고객사1`. 세션 스코프 별칭 사전을 만들고 **응답에서 역치환**한다 |
| P4 | **가능하면 집계값을 보낸다.** "지난달 SUP_A 불량률?" 에 200행을 보내지 않는다. **1행 집계 결과**를 보낸다 (§3.3 Text-to-SQL 이 집계 쿼리를 강제) |

#### 2.8.2 필드 단위 허용목록 (v1.1 — FE-RT-10·20 범위)

**입고 Agent (FE-RT-10)** — 주 대상 `receipts` · `components` · `suppliers` · `lots`

| 테이블 | 송출 허용 | **송출 금지** | 처리 |
|---|---|---|---|
| `receipts` | `receipt_date`, `qty`, `material`, `status`, 성분값(`sn`/`ag`/`cu`/`pb`) | `supplier_code` 원문, `lot_id` 원문, 비고/자유서술 | 공급사·LOT 은 **별칭 치환** |
| `components` | `sn`,`ag`,`cu`,`pb`, `sn_deviation`,`ag_deviation`,`cu_deviation` | `lot_id` 원문 | 별칭 치환 |
| `suppliers` | `primary_material`, `active`, 집계 통계(`avg_quality`,`pass_rate`,`sn_std`…) | **`name`·`contact` — 절대 금지** | `code` → `공급사N` 별칭 |
| `lots` | `production_date`, `status`, `quality_score`, `temperature`, `process_time` | `lot_id` 원문 | 별칭 치환 |

**출하 Agent (FE-RT-20)** — 주 대상 `shipments` · `claims` · `quality` · `lots`

| 테이블 | 송출 허용 | **송출 금지** | 처리 |
|---|---|---|---|
| `shipments` | `ship_date`, `qty`, `status`, `due_date` | **`customer` — 절대 금지**, `lot_id` 원문 | 고객사 → `고객사N`, LOT → `LOT#N` |
| `claims` | `status`, `claim_date`, `reason`(**분류 코드만**), `resolution` 유무 | **`customer` 금지**, `reason` 자유서술 원문, `claim_no` 원문 | 자유서술은 **RAG 청크로만** 접근(§3), 프롬프트에는 발췌 |
| `quality` | `score`, `passed`, `inspect_date`, 검사 항목값 | `lot_id` 원문, 검사자명 | 별칭 치환 |
| `lots` | 위와 동일 | 위와 동일 | 위와 동일 |

**항상 금지 (전 테이블 공통)**
`users.*` 전체 · `password_hash` · `audit_logs.*` · `system_settings` 중 `integration.*` · API 키/토큰류 ·
개인 식별정보(담당자명·연락처·이메일) · `agent_runs.prompt_sent` (재귀 송출 금지).

#### 2.8.3 마스킹 계층은 어디에 두는가

**기존 `src/api/middleware.py` 의 `_REDACT_KEY_FRAGMENTS` 를 재사용하지 않는다. 이유:**

| 항목 | `_REDACT_KEY_FRAGMENTS` (기존, `middleware.py:91`) | Agent 송출 마스킹 (신규) |
|---|---|---|
| 목적 | **감사로그 `detail` JSONB 저장 시** 비밀값 제거 | **외부 API 전송 전** 업무 데이터 최소화 |
| 방식 | **차단목록** — `password`/`secret`/`token`/`api_key`/`apikey`/`credential` 키 이름 부분일치 | **허용목록** — 목록에 없으면 차단 |
| 가역성 | 비가역 (마스킹 후 버림) | **가역** — 별칭 사전으로 응답에서 역치환해야 함 |
| 적용 지점 | 감사 쓰기 경로 | LLM 호출 경로 |

**두 계층은 목적이 다르므로 합치지 않는다.** 단 **`_REDACT_KEY_FRAGMENTS` 는 신규 계층에서도 최종
안전망으로 한 번 더 통과시킨다** — 허용목록이 실수로 비밀값을 허용해도 이름 기반으로 걸린다.

**위치 결정 — `src/agent/redaction.py` (신규 모듈, 프로바이더 어댑터 *안쪽* 경계)**

```
그래프 노드(§5)            ← 별칭이 붙은 데이터만 본다
      ↓ ctx (Evidence[])
  redaction.to_wire(ctx)   ← ★ 허용목록 + 별칭 치환 + _REDACT_KEY_FRAGMENTS 안전망
      ↓ 마스킹된 프롬프트
  LLMProvider.stream()     ← 외부로 나가는 유일한 지점
      ↓ 응답
  redaction.from_wire()    ← 별칭 역치환 (LOT#1 → LOT-2026-001)
      ↓
  룰 검증(§4) → 응답
```

**왜 미들웨어가 아니라 여기인가**: FastAPI 미들웨어는 **HTTP 응답 경로**에만 있다.
외부 API 호출은 요청 처리 **도중**에 일어나므로 미들웨어가 볼 수 없다.
**어댑터 바로 앞이 유일하게 "밖으로 나가는 모든 바이트"가 지나는 지점**이다.

#### 2.8.4 강제 방법 — 설계 규약

| 규약 | 내용 |
|---|---|
| **단일 출구** | `LLMProvider` 구현체는 `redaction.to_wire()` 를 통과하지 않은 문자열을 받으면 **예외를 던진다.** 마스킹은 선택이 아니다 |
| **Evidence 타입 강제** | 그래프 노드는 자유 문자열이 아니라 `Evidence{source_type, source_ref, fields:dict, text:str}` 만 프롬프트에 넣는다. `fields` 는 허용목록으로 필터된 것만 담긴다 |
| **허용목록의 저장 위치** | **코드 상수** (`src/agent/allowlist.py`). `system_settings` 에 두지 않는다 — 런타임에 바뀌면 보안 경계가 런타임에 바뀐다 |
| **테스트 게이트** | 허용목록 밖 컬럼이 `to_wire()` 결과에 등장하면 실패하는 테스트. QA 비기능 케이스로 등재(§8) |
| **감사** | 실제 송출 전문을 `agent_runs.prompt_sent` 에 저장(§6.6). **사후 검증 가능해야 진짜 통제다** |

### 2.9 [G2] API 키 관리 — 미설정 시 거동

|---|---|

| **미설정 시 거동** | **기동은 정상. `/agents/*` 만 501.** ← 아래 근거 |

#### 2.9.1 왜 "기동 거부"가 아니라 "501 유지"인가

**기동 거부를 택하면 안 되는 이유가 명확하다:**

| 이유 | 설명 |
|---|---|
| **44화면 중 36화면이 Agent 와 무관하다** | 키 하나가 없다고 대시보드·입고·배합·출하·KPI 전부를 못 쓰게 만드는 것은 비례하지 않는다 |
| **`api-contract.md` §8.10 이 501 을 이미 규정했다** | 미설정 = 미구현과 **런타임 동작이 동일**해야 계약이 안 깨진다. `NullProvider`(§2.5)가 이 등가성을 보장한다 |
| **CR-ARCH-001 이 미승인이다** | 승인 전에는 **켜지면 안 된다.** 미설정이 안전 기본값이어야 한다 |
| **로컬 회귀(§2.11) 경로 보존** | `AGENT_LLM_PROVIDER=ollama` 로 바꿔도 앱이 기동해야 한다 |

**단, "조용히 501" 은 금지다.** 미설정은 **눈에 보여야 한다**:

| 지점 | 거동 |
|---|---|
| 기동 시 | `WARNING` 1회: `"AGENT_LLM_PROVIDER 미설정 — /agents/* 는 501 을 반환합니다"` |
| `GET /agents/health` | `{"provider": null, "configured": false, "index_ready": false, "reason": "AGENT_LLM_PROVIDER 미설정"}` |
| `POST /agents/*` | `501` + `{"detail": "미구현 — v1 범위 밖"}` (§5 오류 계약 문구 **그대로**. 새 문구를 발명하지 않는다) |
| 화면 | `/agents/health` 응답으로 **"AI 준비 중 — 미구성"** 을 명시 렌더링. **빈 화면·가짜 답변 금지** |

#### 2.9.2 설정 오류의 구분 — 셋을 섞지 마라

| 상황 | 감지 | HTTP | 화면 |
|---|---|---|---|
| 제공자 미설정 | `AGENT_LLM_PROVIDER` 없음 | **501** | "AI 준비 중 — 미구성" |
| 제공자 설정됨 + **키 없음** | `ANTHROPIC_API_KEY` 없음 | **501** | "AI 준비 중 — 인증정보 미설정" |

> **새 오류 코드를 발명하지 않는다** (`api-contract.md` §5: "표의 6줄이 전부다").

### 2.10 [G3] 장애 · 레이트리밋 · 비용 — 외부 의존이 생겼다

> goal.md 3절: **"조용한 실패 금지. `catch {}` 로 하드코딩 결과를 끼워넣지 않는다."**
> 이 프로젝트 최대 결함이 되살아날 수 있는 지점이 정확히 여기다.

#### 2.10.1 실패 유형별 거동

| 실패 | 감지 | HTTP | 응답 본문 | 화면 |
|---|---|---|---|---|
| 인터넷/API 단절 | `APIConnectionError` | **503** | `{"detail":"서비스 일시 중단"}` | "AI 서비스 일시 중단" + **재시도 버튼** |
| 인증 실패(키 무효) | `AuthenticationError` | **503** | 동일 | 동일 + 관리자 문의 |
| 레이트리밋 | `RateLimitError` | **503** | 동일 | "잠시 후 다시 시도" + `retry-after` 초 표시 |
| 벤더 5xx | `APIStatusError >= 500` | **503** | 동일 | 동일 |
| **타임아웃** | `APITimeoutError` (`AGENT_LLM_TIMEOUT_S`) | **200** | `{"answer": null, "answer_status": "timeout", "sources": [...]}` | **"답변 생성 시간 초과 — 아래 근거 문서를 확인하세요"** + 검색된 근거는 그대로 표시 |
| 월 비용 상한 초과 | 자체 카운터(§2.10.3) | **503** | 동일 | "AI 사용량 한도 도달 — 관리자 문의" |

**타임아웃만 200 인 이유**: `api-contract.md` §5 가 이미 같은 판단을 내려 두었다 —
"최적화 수렴 실패 → **200** + `optimization_success: false`. **절대 4xx/5xx 로 바꾸지 마라**".
**타임아웃은 시스템 장애가 아니라 이 질의에 대한 결과**다. 검색된 근거는 유효하므로 버리지 않는다.
§7.5 가 `answer_status` 전체 값 집합을 정의한다.

#### 2.10.2 절대 하지 말 것

| 금지 | 이유 |
|---|---|
| ❌ 실패 시 **캐시된 이전 답변**을 조용히 반환 | 다른 질문의 답이 현재 질문의 답으로 보인다. 조용한 실패의 정확한 재현 |
| ❌ 실패 시 **템플릿 문장**("일반적으로 …") 반환 | 근거 없는 답 = 제1원칙 위반 |
| ❌ `except Exception: pass` 후 빈 `sources[]` 반환 | 실패가 "결과 없음"으로 위장된다 |
| ❌ 프론트 `tryFetch` 에 fallback 부활 | `api-contract.md` §5.2 가 명시적으로 금지 |

#### 2.10.3 비용·사용량 통제

| 통제 | 설계 |
|---|---|
| **모델 선택** | 기본 `AGENT_LLM_MODEL` 환경변수. **코드에 모델 ID 를 박지 않는다.** §2.4 표가 자릿수 판단 근거 |
| **프롬프트 캐싱** | 룰·스키마 프리픽스(약 3,000토큰)를 캐시 대상으로 고정 → 약 31% 절감(§2.4). **캐시는 프리픽스 정확 일치**이므로 프리픽스에 타임스탬프·요청ID·정렬 안 된 JSON 을 넣지 마라 → §4.4 가 이를 규약으로 못박는다 |
| **컨텍스트 예산** | 1건당 입력 상한 **8,000토큰** 하드캡. RAG 청크는 상위 `k=5`(§3.6), 대화이력은 최근 6턴. 초과분은 **자르지 않고 청크 수를 줄인다** (자르면 인용이 깨진다) |
| **출력 상한** | `max_tokens` 기본 1,500. 분석 리포트(FE-RT-39)만 4,000 |
| **월 상한** | `AGENT_MONTHLY_TOKEN_BUDGET` 환경변수. `agent_runs` 의 당월 토큰 합계로 판정. **초과 시 503**(§2.10.1 마지막 행). 상한값은 도입기업이 지정 (CR-ARCH-001 승인사항 ④) |
| **사용량 가시화** | `GET /agents/logs`(FE-RT-42)가 `agent_runs` 를 그대로 노출 — 호출수·응답시간·토큰·비용 추정. **FR-AG-05 와 사업계획서 p.60 "사용 로그 기록·관리"를 동시에 충족** |
| **레이트리밋 대응** | SDK 자동 재시도(기본 2회, 지수 백오프)를 그대로 쓴다. **자체 재시도 루프를 덧붙이지 마라** — 이중 재시도는 타임아웃 벽시계를 배로 늘린다 |

| **6개 선택 화면은 같은 기반에 얹되 게이트 밖** | 스키마(§6)·API(§7)는 8화면 전체를 수용하되, **구현 순서는 10·20 우선**. 나머지는 `NullProvider` 유무와 무관하게 501 을 유지해도 v1.1 게이트를 통과한다 |

#### 2.12.1 두 화면이 정확히 무엇을 답해야 하는가 (사업계획서 원문 기준)

## 3. [B] RAG 인덱스 설계 — 그리고 어디까지가 RAG 인가

> **핵심 질문은 "무엇을 색인할 것인가"가 아니라 "무엇을 색인하지 *않을* 것인가"다.**
> 이 시스템 지식의 대부분은 **18테이블의 정형 데이터**이고, 그건 SQL 로 답해야 정확하다.

### 3.1 사업계획서가 이미 경계를 그어 놓았다

**PDF p.26 「공급기업의 제조 AI 방법론」 ② 단계** (원문):
> "**정형 데이터는 예측 및 추천AI의 입력값으로 활용하고, 비정형 문서는 AI Agent의 질의응답 및
> 작업 가이드 제공에 활용한다.**"

**PDF p.18 「데이터 계층」** — 저장소를 셋으로 나눠 놓았다:

| 계층 | 대상 | 이 프로젝트의 대응 |
|---|---|---|
| ① 정형 (RDBMS) | 생산 실적, LOT 이력, 재고·입출고·출하, 설비 센서 | **PostgreSQL 18테이블 → Text-to-SQL (§3.3)** |
| ② 비정형 (**Vector DB**) | **작업표준서, 배합 레시피, 품질 기준서, 검사 지침서, 클레임 대응 매뉴얼**, 설비 유지보수 이력, 기술 문서 | **pgvector → RAG (§3.4~3.6)** |
| ③ 시계열 (TSDB) | 생산량·불량률 추이 | v1 범위 밖. 정형 테이블의 집계로 대체 |

**이 문서는 그 경계를 그대로 따른다.** 새로 발명하지 않는다.

### 3.2 경계 판정 — 3경로 라우팅

**PDF p.19 이 예시 질문 4개를 직접 적어 놓았다. 이것으로 경계를 검증한다:**

| # | 사업계획서 원문 질문 | 답에 필요한 것 | 경로 | RAG 로 답하면? |
|---|---|---|---|---|
| 1 | *"이 LOT 불량 원인이 뭐야?"* | `lots`+`quality`+`components`+`process_conditions` 조인, 편차 임계 대조 | **SQL + 계산 (+ 규칙)** | ❌ **벡터 검색이 숫자를 못 센다.** 근사 문장을 지어낸다 |
| 2 | *"지금 배합비 최적값 추천해줘"* | `POST /recommend` (SLSQP) 실행 | **도구 호출** | ❌ 최적화는 검색이 아니다 |
| 3 | *"최근 불량이 가장 많이 발생한 공정은 어디야?"* | `GROUP BY` + `ORDER BY count DESC LIMIT 1` | **SQL** | ❌ 상위 k 청크에 "가장 많은" 정답이 있을 보장이 0 |
| 4 | *"이 제품 공정 이력 추적해줘"* | LOT 기준 다중 테이블 조인 | **SQL** | ❌ 동일 |

> 🔴 **사업계획서가 예시로 든 4개 질문 중 RAG 로 답해야 할 것은 0개다.**
> 이것이 "RAG 기반 AI Agent"라는 이름에 속으면 안 되는 이유다.
> **RAG 는 이 시스템에서 소수 경로다.** 다수 경로는 Text-to-SQL 이다.

#### 3.2.1 판정 규칙 (질문 분류 노드가 쓰는 규칙)

| 경로 | 언제 | 특징 신호 |
|---|---|---|
| **SQL** | 답이 **DB 에 행으로 존재**한다 | 수치·개수·순위·기간·비교·추이·특정 LOT/공급사/고객사·"몇 건"·"가장"·"평균"·"지난달" |
| **RAG** | 답이 **문서 문장에 있다** | 절차·기준·정의·규정·대응 방법·"어떻게 해야"·"기준이 뭐야"·"규격"·"매뉴얼" |
| **TOOL** | 답을 **계산해야 한다** | 예측·추천·최적화 → 기존 `/predict`·`/recommend` 재사용. **새로 만들지 않는다** |
| **HYBRID** | 위 둘 이상이 필요하다 | "이 LOT 이 품질 기준을 만족하나?" = SQL(실측값) + RAG(기준서) |
| **REFUSE** | 어느 경로도 근거를 못 준다 | §4.6 "모르겠다" |

#### 3.2.2 애매한 경계 — 미리 판정해 둔다

| 질문 유형 | 판정 | 이유 |
|---|---|---|
| "지난달 불량 LOT 원인은?" | **SQL + 규칙** (RAG 아님) | 원인 후보는 **편차 임계(2.0/0.3/0.1) 초과 여부**와 **온도 255°C 초과 여부**로 **계산**한다. 문서에 답이 없다 |
| "SUP_A 성분 편차가 큰가?" | **SQL** | `components` 표준편차 집계 + 임계 대조 |
| "이 클레임 어떻게 대응해?" | **RAG** | 클레임 대응 매뉴얼 문장 |
| "이 클레임과 비슷한 과거 사례?" | **SQL** | `claims` 테이블 검색. 유사도 검색이 아니라 **필터** |
| "SAC305 규격이 뭐야?" | **RAG** (`master_codes.QUALITY_STD` 또는 품질기준서) | 정의성 질문 |
| "LOT-2026-001 이 SAC305 규격에 맞나?" | **HYBRID** | SQL(`components` 실측) + RAG/규칙(기준값) 대조 |
| "모델 정확도가 얼마야?" | **규칙 고정값** | §4.3 R6 — **SF-TI2 실측 `R²=0.782` 를 강제**. LLM 이 기억으로 답하지 못하게 한다 |

> **RAG 를 정형 질의에 쓰지 않는 이유를 한 줄로**: 벡터 검색은 **의미 유사도 상위 k 개**를 준다.
> 그건 "관련 있어 보이는 것"이지 **"정답"이 아니다.** 개수·최대·평균은 유사도로 구할 수 없다.

### 3.3 Text-to-SQL 설계 — v1.1 범위 (FE-RT-10·20 한정)

> §2.12 결정에 따라 **18테이블 전체를 여는 범용 SQL 에이전트를 만들지 않는다.**

#### 3.3.1 노출 테이블 (화면별 화이트리스트)

| 화면 | 노출 테이블 | 근거 |
|---|---|---|
| **FE-RT-10 입고** | `receipts` · `components` · `suppliers` · `lots` | 사업계획서 p.23 입력(정형) = "재고량, 입고이력, LOT 정보, 생산 연계 데이터" |
| **FE-RT-20 출하** | `shipments` · `claims` · `quality` · `lots` | p.24 입력(정형) = "출하이력, 품질검사 데이터, LOT 정보, 고객정보" |

**두 화면 모두에서 접근 불가**: `users` · `audit_logs` · `system_settings` · `ml_models` ·
`notification_rules` · `condition_history` · `kpi_targets` · `master_codes`(값은 룰 주입으로만, §4).

#### 3.3.2 생성 금지 — SQL 을 LLM 이 자유 작성하지 않는다

**v1.1 은 자유 SQL 생성을 채택하지 않는다.** 대신 **파라미터화된 쿼리 카탈로그**를 쓴다.

| 방식 | v1.1 채택 | 이유 |
|---|---|---|
| ❌ 자유 Text-to-SQL (LLM 이 SQL 문자열 생성 → 실행) | 미채택 | ① **NFR-S-05 "SQL Injection 방지 — ORM 사용, 파라미터 바인딩"** 과 충돌한다. LLM 이 만든 문자열을 실행하는 것은 SQL 인젝션의 정의 그 자체다 ② 검증 비용이 실익보다 크다 ③ 잘못된 조인이 **틀린 숫자를 자신 있게** 내놓는다 — 가장 위험한 실패 |
| ✅ **쿼리 카탈로그 + 파라미터 추출** | **채택** | LLM 은 **"어느 쿼리 + 어떤 파라미터"만 고른다.** SQL 은 개발자가 SQLAlchemy 로 미리 작성 |

**동작**: LLM 에게 도구 목록을 준다 → LLM 이 도구 1개와 인자를 고른다 → 서버가 **미리 작성된 ORM 쿼리**를 실행 →
결과를 허용목록(§2.8)으로 필터해 `Evidence` 로 만든다.

|---|---|

**→ `DEF-AR-007` 로 등재한다** (§8). **코퍼스 확보가 RAG 구현의 선행 조건이다.**

| 결정 | 내용 |
|---|---|
| D1 | **`docs/산출물/` 16종을 v1.1 색인 대상에 넣지 않는다.** 현장 질문("자재 입고 기준이 뭐야")에 설계서 문장을 근거로 답하면 **그럴듯하지만 틀린 답**이 나온다. §2.12 "범용 설계로 부풀리지 않는다"와 같은 판단 |
| D2 | **v1.1 은 S1·S2 (DB 소재 `master_codes`) 만으로 시작한다.** 이미 존재하고, 화면(FE-RT-30·31)으로 갱신 가능하며, 버전 관리가 된다 |
| D3 | **S3~S6 은 파일 업로드 경로를 열어 두되(§7.3 `POST /agents/documents`), 문서 확보 후 색인한다.** 문서가 없으면 색인이 비어 있고, `GET /agents/health` 가 `index_ready:false` 를 그대로 보여준다 |
| D4 | **인덱스가 비어 있을 때 RAG 경로는 "모르겠다"를 반환한다.** 그것이 정직한 동작이다 (§4.6) |

> **코퍼스 규모 예상**: S1~S6 확보 후에도 수백 KB 수준. 청크 400토큰 기준 **수백~2,000 청크**.
> 이 규모는 §3.5 벡터 저장소 선택에 결정적이다 — **어떤 저장소든 성능 문제가 없다.**

### 3.5 벡터 저장소 — `pgvector` vs 별도(Chroma/FAISS)

| 축 | **`pgvector` (권고·채택)** | Chroma | FAISS |
|---|---|---|---|
| **사업계획서 p.20 명세** | ✅ **"Vector DB / PostgreSQL, pgvector" 로 이미 명시** | ❌ 명세와 불일치 | ❌ 동일 |
| 신규 인프라 | **없음.** 기존 PostgreSQL 17 에 확장만 설치 | 별도 서버/프로세스 | 라이브러리(프로세스 내) |
| **트랜잭션 정합** | ✅ `doc_sources`·`doc_chunks`·`agent_citations` 가 **같은 트랜잭션** | ❌ 2-phase 필요. 색인 실패 시 불일치 | ❌ 동일 |
| **인용 조인** | ✅ 청크 → `master_codes.id` → 화면 링크를 **SQL 조인 한 번**으로 | ❌ 애플리케이션 조인 | ❌ 동일 |
| 백업·복구 | ✅ **기존 `pg_dump` 정책(SF-TD5 §5, 90일)에 자동 포함** | ❌ 별도 백업 체계 필요 | ❌ 파일 관리 직접 |
| RBAC·감사 | ✅ 기존 DB 권한·감사 체계 그대로 | ❌ 별도 | ❌ 없음 |
| 성능 (수천 청크) | ✅ 충분. HNSW 인덱스로 수만 건까지 문제없음 | ✅ | ✅ 최고 (수천만 건 규모에서) |
| 운영 부담 | 낮음 (테이블 2개 추가) | 중 (서비스 1개 추가) | 중 (영속화·재빌드 직접 구현) |
| **설치 부담** | ⚠ **PostgreSQL 17 에 `pgvector` 미제공** — `apt install postgresql-17-pgvector` / `brew install pgvector` 필요 | pip 설치 | pip 설치 |

**권고: `pgvector`.** 근거 3가지 —
① **사업계획서 p.20 이 이미 지정**했다(DEF-AR-004 복원). ② 코퍼스가 수천 청크 규모라 **FAISS 의 성능 이점이 발현되지 않는다.**
③ **인용이 이 시스템의 생명선**(§3.8)인데, 청크와 원본 레코드가 같은 DB 에 있어야 인용이 깨지지 않는다.

**유일한 비용**: 확장 설치 1회. **`CR-DB-007` 승인사항에 포함**한다(§6).
확장이 없으면 마이그레이션이 실패하므로, Alembic 리비전 첫 줄에 `CREATE EXTENSION IF NOT EXISTS vector;` 를 두고
**실패 시 명확한 메시지로 중단**시킨다 (조용히 건너뛰지 않는다).

### 3.6 청킹 · 임베딩 · 검색 파라미터

| 항목 | 값 | 근거 |
|---|---|---|
| **청킹 단위** | **구조 우선 분할.** `master_codes` 는 **1레코드 = 1청크**(자를 이유가 없다). 문서 파일은 **제목(헤딩) 경계 우선**, 헤딩 없으면 문단 | 인용이 "문서 3쪽 어딘가"가 아니라 **"작업표준 WS-01 v3 §2"** 를 가리켜야 한다 |

| **거리** | 코사인 | — |
| **검색** | **k=5**, 유사도 하한 컷오프 적용 | 상한은 §2.10.3 컨텍스트 예산에서 옴 |

### 3.7 재색인 — 언제 다시 만드는가

| 트리거 | 범위 | 방식 |
|---|---|---|
| `master_codes` **쓰기** (FE-RT-30·31·32 화면에서 발생) | **해당 레코드 1건** | **이벤트 기반 증분.** 저장 성공 직후 해당 `id` 의 청크를 삭제 후 재생성 |

### 3.8 인용(citation) 계약 — "지어내지 않는다"의 실행 형태

| 규칙 | 내용 |
|---|---|
| **C-1** | 사실 주장을 담은 답변은 `Evidence` 를 **1건 이상** 동반한다. 근거 0건이면 답변을 내지 않는다(C-5·§4.6). 🔴 **문장↔근거 매핑(`spans`)과 인라인 마커(`[1]`)는 v1.1 계약에 넣지 않는다** — §7.12 |
| **C-2** | 인용은 **화면에서 클릭 가능**해야 한다. RAG 청크 → `master_codes` 레코드 또는 문서+위치. SQL 결과 → 도구명 + 인자 + 원본 화면 링크(예: `/receiving/history?lot_id=…`) |
| **C-3** | **인용은 답변과 함께 저장된다** (`agent_citations`, §6.5). 사후에 "이 답의 근거가 뭐였나"를 재현할 수 있어야 한다 |
| **C-4** | 인용 원문(`snippet`)을 저장한다. **원본이 나중에 바뀌어도 그때 무엇을 보고 답했는지가 남는다** |
| **C-5** | 근거 0건 → **답변 생성 자체를 하지 않는다.** LLM 을 부르지 않고 `no_evidence` 를 반환한다 (§4.6) — 부르지 않으면 지어낼 수 없다 |

**`Evidence` 계약 (§2.8.4 와 동일 타입)**

```
Evidence
  kind        : "sql" | "doc"
  source_ref  : 도구명+인자 해시  |  doc_chunks.id
  label       : 화면 표시용 라벨 ("공급사 편차 통계(최근 90일)" / "작업표준 WS-01 v3 §2")
  link        : 프론트 라우트 (클릭 가능해야 한다)
  fields      : 허용목록 통과 필드만 (§2.8)
  snippet     : 인용 원문 발췌 (문서일 때)
```

## 4. [C] Rule DB — 룰을 어디에 두고, 어떻게 주입하고, 어떻게 막는가

> **이 시스템에는 이미 하드 룰이 계약으로 존재한다** (goal.md 2.3).
> 문제는 룰을 *새로 만드는 것*이 아니라, **Agent 가 그 룰을 어기지 못하게 하는 것**이다.

### 4.1 룰은 이미 3곳에 산다 — **4번째 집을 만들지 않는다**

| 계층 | 저장 위치 | 예 | 변경 가능성 |
|---|---|---|---|
| **L1 불변 상수** | **코드** — `src/features/engineering.py` | `SN_TARGET=62.0` · `AG_TARGET=3.0` · `CU_TARGET=0.5` | 🔴 **런타임 변경 불가.** 저장 모델 4개의 파생 피처가 이 값으로 굳어 있다 (`db-schema.md` §6.8) |
| **L2 운영 가변** | **`system_settings`** (실측 키, `src/api/settings_store.py`) | `quality.pass_score=70` · `quality.warn_score` · `equipment.temp_warn_c=255` · `deviation.warn_sn/ag/cu` · `ml.sn/ag/cu_target`(읽기 전용) | ✅ FE-RT-29 화면에서 변경 |
| **L3 서술형 지식** | **`master_codes`** | `QUALITY_STD` JSONB(`sn_min/max`,`pass_score`…) · `WORK_STD` 본문 | ✅ FE-RT-30·31 화면에서 변경 |
| **L4 코드 경계** | **코드** — `src/models/optimize.py` + API 레이어 | 최적화 경계 Sn 55~70 · Ag 1~5 · Cu 0.1~1.5 · Pb 25~45 | 🔴 계약값 (goal.md 2.3) |

#### 🔴 결정 — **신규 `agent_rules` 테이블을 만들지 않는다**

| 이유 | 설명 |
|---|---|
| **드리프트가 최대 위험이다** | 합격선 70 이 `system_settings` 와 `agent_rules` 두 곳에 있으면, 화면(FE-RT-29)에서 75 로 바꿔도 Agent 는 70 이라고 계속 답한다. **Agent 가 시스템과 다른 말을 하는 것**이 최악의 결함이다 |
| **이미 정본이 있다** | goal.md 2.3 · `system_settings` · `master_codes` 가 정본이다. 복제본은 정본이 아니라 **경쟁자**다 |
| **`api-contract.md` §9.1 의 교훈** | 아키텍트가 `master_codes` JSONB 정당화를 철회한 근거와 같다 — "절감된 건 DDL 뿐이고 대신 검증이 늘어난다" |

**대신 — `RuleSnapshot` 조립기.** 요청마다 L1~L4 를 **읽어서** 하나의 불변 객체로 조립한다.
저장소가 아니라 **뷰**다. 이 스냅샷 하나가 ① 프롬프트 주입 ② 출력 검증 ③ 감사 기록에 **모두 쓰인다.**

```
RuleSnapshot  (요청마다 조립, 불변)
  pass_score          70      ← system_settings quality.pass_score
  warn_score          …       ← system_settings quality.warn_score
  temp_warn_c         255     ← system_settings equipment.temp_warn_c
  dev_warn            {sn:2.0, ag:0.3, cu:0.1}   ← system_settings deviation.*
  targets             {sn:62.0, ag:3.0, cu:0.5}  ← engineering.py (L1, 읽기전용)
  ratio_sum           100.0 ± 0.05                ← 계약 상수
  opt_bounds          {sn:(55,70), ag:(1,5), cu:(0.1,1.5), pb:(25,45)}  ← 계약 상수
  model_r2_official   0.782   ← §4.3 R6
  model_rmse_official …       ← SF-TI2 실측
  quality_std         {…}     ← master_codes QUALITY_STD (활성 버전)
  snapshot_hash       sha256  ← agent_runs 에 기록. "어떤 룰로 답했나"를 재현
```

**유일한 신규 저장 항목** — 기존 3곳 어디에도 자리가 없는 값들:

| 신규 키 | 값 | 위치 | 이유 |
|---|---|---|---|
| `agent.model_r2_official` | `0.782` | **`system_settings`** (`agent.` 네임스페이스 신설) | §4.3 R6. `ml_models` 테이블의 학습 시점 지표와 **SF-TI2 실측 인용값은 다른 것**이다 |
| `agent.model_rmse_official` | SF-TI2 실측값 | 동일 | 동일 |
| `agent.max_rows` | `50` | 동일 | §3.3.3 |
| `agent.retrieval_k` | `5` | 동일 | §3.6 |

> `settings_store.py` 의 `SETTINGS_PREFIXES` 에 `"agent."` 를 **추가**한다. 테이블 변경 없음.
> `system_settings` 는 `key VARCHAR(50)` PK 의 키-값 저장소이므로 **DDL 변경이 필요 없다.**
> **API 키는 여기 넣지 않는다** (§2.9 · `db-schema.md` §6.8).

### 4.2 룰 주입 — 프롬프트의 어디에 넣는가

| 항목 | 결정 |
|---|---|
| **위치** | **시스템 프롬프트의 프리픽스**. 질문·RAG 청크·대화이력보다 **앞**이다 |
| **왜 앞인가** | ① 권위(모델은 앞선 지시를 상위로 취급) ② **프롬프트 캐싱이 프리픽스 정확 일치**라서(§2.10.3) — 룰 블록이 앞에 고정돼야 약 31% 절감이 발생한다 |
| **형식** | 결정적 직렬화. **키 정렬 고정, 값 포맷 고정.** 타임스탬프·요청ID·`json.dumps` 기본 순서 금지 — 한 바이트만 달라도 캐시가 전부 무효가 된다 |
| **분량** | 약 3,000 토큰 (룰 + 도구 스키마 + 인용 규약 + 거절 규약) |
| **주입 대상** | **답변 생성 노드에만.** 질문 분류 노드는 룰이 필요 없다 (짧고 싸게 유지) |

> ⚠ **룰 주입은 방어가 아니라 안내다.** LLM 은 지시를 어길 수 있다.
> **강제는 §4.5 출력 검증이 한다.** 주입만 하고 검증을 생략하면 아무것도 강제되지 않는다.

### 4.3 프롬프트에 들어가는 룰 (R1~R8)

| ID | 룰 | 근거 |
|---|---|---|
| **R1** | 품질 합격선은 **`{pass_score}`점**. 미만은 불합격. **이 숫자를 다른 값으로 말하지 마라** | goal.md 2.3 · `system_settings` |
| **R2** | 배합 성분 합계는 **정확히 100.0%** (허용오차 ±0.05) | goal.md 2.3 |
| **R3** | 최적화 경계: Sn 55~70 · Ag 1~5 · Cu 0.1~1.5 · Pb 25~45. **경계 밖 배합비를 제시하지 마라** | goal.md 2.3 |
| **R4** | 편차 경고 임계: Sn ±2.0 · Ag ±0.3 · Cu ±0.1. 성분 목표: Sn 62.0 · Ag 3.0 · Cu 0.5 | goal.md 2.3 |
| **R5** | 용해 온도 입력 200~320°C, **255°C 초과 시 경고** | goal.md 2.3 |
| **R6** | 🔴 **모델 성능을 말해야 하면 `R²={model_r2_official}` (SF-TI2 실측)을 쓴다.** `0.874`·`0.85 달성` 등 다른 수치를 절대 인용하지 마라 | 아래 §4.3.1 |
| **R7** | **근거 없이 답하지 마라.** 제공된 `Evidence` 밖의 사실을 만들지 마라. 근거가 없으면 "확인할 수 없습니다"라고 답하라 | goal.md 3절 |
| **R8** | **판정하지 마라. 근거를 제시하라.** 출하 적합/불합격 최종 판단은 사람이 한다 | 사업계획서 p.26 "의사결정 지원형 AI" |

#### 4.3.1 R6 을 별도로 강제하는 이유

| 수치 | 출처 | Agent 인용 |
|---|---|---|
| `R² = 0.874` | **합성 데이터 성능** | 🔴 **금지** |
| `R² ≥ 0.85` | SF-AD1 **목표치** | 🔴 금지 (합격선이 아니다) |
| `R² ≥ 0.60` | SF-AD2 NFR-P-05 **계약 게이트** | ✅ "게이트"로만 인용 가능 |
| **`R² = 0.782`** | **SF-TI2 시스템전환결과서 실측** | ✅ **성능을 말할 때 유일하게 허용** |

`api-contract.md` §7.4 가 이미 "**이 수치를 실데이터 성능으로 인용하지 마라**"를 규정했다.
사람에게 한 경고를 **LLM 에게도 똑같이 적용**하고, **§4.5 V3 이 출력에서 강제**한다.

`RuleSnapshot.snapshot_hash` 가 바뀌면 캐시 미스가 예상된다는 것을 운영이 알 수 있게 `agent_runs` 에 기록한다.

### 4.5 출력 검증 — **답변이 룰을 어겼을 때 어떻게 막는가**

> **여기가 이 절의 핵심이다.** 주입은 부탁이고, **검증만이 강제다.**
> 검증기는 결정적 코드다. **LLM 에게 자기 답을 검사시키지 않는다.**

| ID | 검증 | 방법 | 위반 시 |
|---|---|---|---|
| **V1 수치 대조** | 답변에서 추출한 수치가 룰 값과 모순되지 않는가 | 정규식으로 "합격선/합격 기준" 근방 숫자, "경고 온도" 근방 숫자, 편차 임계 숫자를 추출 → `RuleSnapshot` 과 대조 | **차단** |
| **V2 인용 필수** | 사실 주장이 있는데 `Evidence[]` 가 비어 있지 않은가 | **답변 단위 검사.** 수치·날짜·LOT·공급사·고객사가 등장하는데 `Evidence[]` 가 0건이면 위반. 🔴 **문장별 인라인 마커를 요구하지 않는다** (§7.12) | **차단** |
| **V3 금칙 수치** | `0.874` · `R² ≥ 0.85 달성` 등 금지 인용이 있는가 | 금칙 패턴 목록 대조 (§4.3.1) | **차단** |
| **V4 배합 경계** | 답변이 배합비를 제시했다면 R3 경계 안인가 | 성분값 추출 → 경계 대조 | **차단** |
| **V5 합계 100%** | 배합비 4개를 제시했다면 합이 100.0±0.05 인가 | 합산 검증 | **차단** |
| **V6 판정 금지** | "출하 가능합니다"·"합격입니다" 같은 **단정 판정**을 내렸는가 | 판정 어구 패턴 + 근거 유무 | **차단** (§2.12.1 · 사업계획서 p.26) |
| **V7 인용 무결성** | 답변이 **본문에서 언급한** 문서명·도구명·라벨이 실제 `Evidence` 집합에 있는가 | 언급 라벨 집합 ⊆ 수집 라벨 집합. 마커가 아니라 **본문 언급**을 본다 (마커는 v1.1 에 없다) | **차단** (없는 근거를 지어낸 경우) |
| **V8 허용목록 역류** | 응답에 별칭 역치환 실패 흔적(`LOT#3` 등)이 남아 있는가 | 별칭 패턴 잔존 검사 | **경고 + 정리 후 통과** |
| **V9 근거 자격** | `doc` 근거에 `snippet` 이, `data` 근거에 `count` 가 있는가 | 없으면 해당 `Citation` 제거. 남은 근거 0건이면 위반 | **해당 근거 제거 → 0건이면 차단** (§7.11.3) |

#### 4.5.1 위반 처리 흐름

```
답변 생성 → 검증기(V1~V8)
   │
   ├─ 통과 ────────────────────────────────→ 응답 (answer_status="ok")
   │
   ├─ 위반 (1회차) → 위반 항목을 명시해 재생성 1회
   │                    │
   │                    ├─ 통과 → 응답 (answer_status="ok", regenerated=true)
   │                    └─ 재위반 ↓
   │
   └─ 재위반 → 🔴 답변을 **버린다**
               응답: { answer: null,
                       answer_status: "rule_violation",
                       violations: ["V1: 합격선을 75로 서술 (정본 70)"],
                       sources: [...] }        ← 근거는 그대로 준다
               HTTP: 200
```

| 결정 | 근거 |
|---|---|
| **재생성은 1회만** | 무한 루프 방지 + 비용·지연 상한(§2.10.3). 2회 시도해 안 되면 모델이 못 하는 것이다 |
| **위반 답변을 부분 노출하지 않는다** | 틀린 문장을 지우고 나머지를 보여주면 **어디가 지워졌는지 사용자가 모른다.** 통째로 버린다 |
| **근거(`sources`)는 남긴다** | 검색 결과 자체는 유효하다. 사용자가 원문을 직접 볼 수 있어야 한다 |
| **HTTP 200** | §5 오류 계약에 없는 코드를 발명하지 않는다. "최적화 수렴 실패 → 200 + `success:false`" 와 동일한 판단 |
| **전량 기록** | 위반 내용·원본 답변을 `agent_runs.violations`·`raw_answer` 에 저장(§6.6). **버린 답도 남는다** — 사후 튜닝의 유일한 재료 |

### 4.6 "모르겠다"를 구조로 만든다

> goal.md 3절: **"지어내지 않는다. 없으면 비운다."** 이 원칙의 Agent 판이다.

| 상황 | 거동 | LLM 호출 |
|---|---|---|
| RAG 유사도 하한 미달 + SQL 결과 0행 | `answer_status="no_evidence"`, `answer="답변에 필요한 근거를 찾지 못했습니다."` | 🔴 **호출하지 않는다** |
| 인덱스가 비어 있음 (§3.4.2 D4) | 동일 + `"AI 지식 문서가 아직 등록되지 않았습니다"` | 호출하지 않는다 |
| 질문이 3경로 어디에도 안 맞음 (REFUSE) | `answer_status="out_of_scope"` + **이 화면이 답할 수 있는 것 안내** | 호출하지 않는다 |
| SQL 결과는 있으나 질문에 답하기엔 부족 | LLM 이 R7 에 따라 "확인할 수 없습니다"를 생성 → V2 통과 | 호출한다 |

**설계 핵심**: 근거가 없으면 **LLM 을 아예 부르지 않는다.**
부르지 않으면 지어낼 수 없다. **환각 방지의 가장 확실한 방법은 생성 기회를 주지 않는 것**이다.

#### 5.2.1 노드 계약

| 노드 | 입력 | 출력 | 실패 시 |
|---|---|---|---|

| **N3 retrieve** | 질의 임베딩 | 청크 ≤5 (컷오프 통과분) | 임베딩 실패 → RAG 근거 0건 (전체 실패로 만들지 않는다) |

| **N8 respond** | 전부 | 응답 + DB 저장 | 저장 실패는 **응답을 실패시키지 않는다** (감사 미들웨어와 같은 원칙) |

#### 5.2.2 근거를 어떻게 되돌려주는가

**규칙: 근거는 답변의 부산물이 아니라 답변보다 먼저 확정된다.**

| 시점 | 무슨 일 |
|---|---|
| N5 종료 | `Evidence[]` 가 **확정되고 id 가 부여된다.** 이후 변하지 않는다 |
| N6 | LLM 은 **이미 확정된 id 만 참조**할 수 있다. 새 근거를 만들 수 없다 |
| N7 V7 | 답변이 참조한 id 집합 ⊆ N5 의 id 집합 인지 검사 → 아니면 차단 |
| N8 | `Evidence[]` → `agent_citations` 저장(§6.5). `snippet` 원문 포함(C-4) |
| 스트리밍 | **`sources` 이벤트를 답변 텍스트보다 *먼저* 보낸다** (§7.4) — 화면이 근거 패널을 먼저 그린다 |

> **왜 근거를 먼저 보내는가**: 사용자는 답이 나오는 동안 근거를 읽을 수 있고,
> 답변이 타임아웃·룰위반으로 버려져도 **근거는 이미 화면에 있다.** 열화 모드가 자연스러워진다.

#### 5.2.3 실패·타임아웃·룰 위반 — 각각 어떻게 되는가

| 사건 | 어느 노드 | HTTP | `answer_status` | 근거 | 화면 |
|---|---|---|---|---|---|
| DB 연결 실패 | N2 | **503** | — | — | "서비스 일시 중단" (§5 기존 행) |
| SQL 타임아웃(3초) | N2 | 200 | `ok` (부분) | 있음 | 답변 + **"일부 데이터를 조회하지 못했습니다"** 배너 |
| 임베딩 API 실패 | N3 | 200 | `ok` 또는 `no_evidence` | SQL 근거만 | 답변 + "문서 검색 불가" 배너 |
| ML 모델 파일 없음 | N4 | **404** | — | — | "모델을 찾을 수 없습니다" (§5 기존 행) |
| **근거 0건** | N5 | 200 | `no_evidence` | 빈 배열 | **"근거를 찾지 못했습니다"** — LLM 미호출 |
| **LLM 타임아웃** | N6 | 200 | `timeout` | 있음 | "생성 시간 초과 — 근거 확인" |
| LLM API 장애·레이트리밋 | N6 | **503** | — | — | "AI 서비스 일시 중단" + 재시도 (§2.10.1) |

### 5.4 🔴 판단 — **LangGraph 가 정말 필요한가**

#### 5.4.1 사업계획서는 LangGraph 를 지정했다

PDF p.20 「클라우드 SW 명세」 AI 서버: **"LangCHain, LangGraph, Prophet, Python"**.
**따라서 미채택은 명세 이탈이고, 이탈에는 근거가 있어야 한다.**

#### 5.4.2 LangGraph 가 값을 하는 조건 vs v1.1 실제

| LangGraph 의 강점 | v1.1 에 해당하는가 |
|---|---|
| 다분기 조건부 엣지 | ⚠ **분기 1개(4갈래).** `if/elif` 로 충분하다 |
| **모델 주도 반복 루프** (계획→실행→재계획) | ❌ **없다.** 재생성 1회는 루프가 아니라 `for _ in range(2)` 다 |
| **체크포인트·재개** | ❌ **불필요.** 대화 재개는 `agent_messages` 조회지 그래프 상태 복원이 아니다. 세션 타임아웃도 30분(NFR-S-01)이라 장기 실행이 없다 |
| **Human-in-the-loop 중단·승인** | ❌ **없다.** p.26 "의사결정 지원형" — Agent 가 행동하지 않으므로 승인 게이트가 없다 |
| 병렬 팬아웃 | ⚠ HYBRID 의 N2+N3 **2갈래뿐.** `asyncio.gather` 로 충분 |
| 노드 단위 스트리밍 상태 | ⚠ 필요하지만 **SSE 이벤트를 직접 쏘면 된다**(§7.4) |
| 다중 에이전트 | ❌ **없다.** §2.12 가 "범용 설계로 부풀리지 않는다"를 결정 |

#### 5.4.3 비용 쪽

| 비용 | 내용 |
|---|---|
| 의존성 | `langgraph` + `langchain-core` 및 그 전이 의존. FastAPI·SQLAlchemy 2·Pydantic 과의 버전 정합을 **매 업그레이드마다** 확인해야 한다 |
| **유지보수 인력** | 사업계획서 p.53 교육 대상은 **대표 1 + 대리 2 = 3명**, AI Agent 교육 총 6시간. 프레임워크 추상화 한 겹이 장애 시 **디버깅 표면을 넓힌다** |
| 대체 비용 | 7노드 선형+1분기+1루프의 **명시적 파이프라인은 파이썬 300줄 안쪽**이고, 스택 트레이스가 곧 그래프다 |

#### 5.4.4 판정

> ### **v1.1 은 LangGraph 를 도입하지 않는다. 단, 그래프 구조는 그대로 유지한다.**

| 결정 | 내용 |
|---|---|
| **채택** | **명시적 파이프라인** — `src/agent/graph.py` 에 노드를 **함수로**, 엣지를 **선언적 라우팅 표(dict)로** 둔다. 그래프는 **데이터로 존재**하고 실행기는 단순 루프다 |
| **왜** | v1.1 의 실제 요구(§5.4.2)에서 LangGraph 고유 기능 **6개 중 4개가 해당 없음**, 2개가 "대체 가능". **얻는 것보다 의존성·디버깅·인력 비용이 크다** |
| **미채택이 아니다 — 연기다** | 노드 시그니처를 `(state) -> state` 로 고정하고 엣지를 데이터로 두면, **LangGraph 전환은 실행기 교체 한 번**이다. 노드 함수는 재작성 대상이 아니다 |
| **`LangChain` 도 미채택** | 리트리버·체인 추상화를 쓰지 않는다. pgvector 는 **SQLAlchemy 로 직접** 질의한다 — 기존 스택과 같은 도구를 쓰는 편이 이 팀에 맞다 |

#### 5.4.5 LangGraph 로 전환하는 트리거 (미리 정해 둔다)

**아래 중 하나라도 발생하면 그때 전환한다. 그 전에는 하지 않는다.**

| # | 트리거 | 해당 화면 |
|---|---|---|
| T1 | **모델 주도 다단 루프**가 필요해짐 (계획→도구→재계획, 반복 3회 이상) | FE-RT-40 의사결정 지원이 깊어질 때 |
| T2 | **Human-in-the-loop 승인 게이트**가 필요해짐 (p.26 "의사결정 지원형" 원칙이 바뀔 때) | 자율 실행 도입 시 |
| T3 | **장기 실행 + 재개**가 필요해짐 (분 단위 리포트 생성) | FE-RT-39 분석 리포트 |

> 도입기업에 **"v1.1 은 미도입, T1~T5 발생 시 도입"** 을 보고한다. **조용히 빠뜨리지 않는다.**

### 7.4 스트리밍 — 필요한가

> **판정: 필요하다. 단 `/agents/receiving`·`/agents/shipping`·`/agents/query`·`/agents/analysis`·`/agents/decision` 5개만.**
> GET 계열 3개(`recommendations`·`logs`·`sessions`)는 **평범한 페이징 조회**다 — 스트리밍 대상이 아니다.

| 근거 | 내용 |
|---|---|
| **답변이 길다** | 500~1,500 토큰. 비스트리밍이면 **완성까지 화면이 멈춘다** |
| **NFR-P-01(2초)를 물리적으로 못 지킨다** | 생성 완료는 5~20초. 스트리밍이면 **TTFT 1~3초**로 "응답이 시작됐다"를 만족시킨다 |
| **근거를 먼저 줄 수 있다** | §5.2.2 — `sources` 이벤트를 텍스트보다 먼저 보내면 사용자가 답을 기다리며 근거를 읽는다 |
| **타임아웃이 부분 손실로 끝난다** | 30초에 끊겨도 그때까지 나온 텍스트 + 근거가 화면에 남는다 |

| 🔴 **룰 위반 시 화면이 텍스트를 지운다** | `status` 이벤트가 `rule_violation` 이면 **프론트가 스트리밍으로 표시한 텍스트를 제거하고 위반 사유·근거만 남긴다.** 이 동작을 계약으로 명시한다 — 명시하지 않으면 위반 답변이 화면에 남는다 |
| **재생성은 스트리밍하지 않는다** | 1회차가 위반이면 2회차는 **비스트리밍**으로 받아 검증 후 통째로 교체한다. 텍스트가 두 번 흐르면 사용자가 혼란스럽다 |
| **비스트리밍 경로도 유지** | `stream=false` 가 기본. QA·통합테스트·`curl` 검증이 단순해진다 |
| **`error` 이벤트 ≠ HTTP 오류** | 헤더가 이미 나갔으므로 상태코드를 바꿀 수 없다. `error` 이벤트로 보내고 **화면이 명시적으로 표시**한다. 조용히 끊지 않는다 |

### 7.5 `answer_status` 값 집합 (닫힌 집합 — 새 값을 발명하지 마라)

| 값 | 의미 | HTTP | `answer` | `sources` |
|---|---|---|---|---|
| `ok` | 정상 | 200 | 문자열 | 1건 이상 |
| `no_evidence` | 근거 0건 — **LLM 미호출** | 200 | **null** | 빈 배열 |
| `out_of_scope` | 이 화면이 답할 수 없는 질문 | 200 | **null** | 빈 배열 |
| `timeout` | 생성 시간 초과 | 200 | **null** 또는 부분 | 있음 |
| `rule_violation` | 룰 검증 재위반 → 답변 폐기 | 200 | **null** | 있음 |

> **5개가 전부다.** `api-contract.md` §5 가 "표의 6줄이 전부다. 새 오류 코드를 발명하지 마라"고 한 것과 같은 규율을 적용한다.

### 7.6 오류 계약 — §5 를 그대로 재사용한다

| 상황 | HTTP | 본문 | §5 어느 행인가 |
|---|---|---|---|
| 제공자 미설정 / 키 없음 | **501** | `{"detail":"미구현 — v1 범위 밖"}` | §5.1 "저장 테이블 없는 화면(선택)" 행 **문구 그대로** |
| LLM API 장애·인증실패·레이트리밋·5xx | **503** | `{"detail":"서비스 일시 중단"}` | §5 "DB 연결 실패" 행 재사용 |
| 월 토큰 상한 초과 | **503** | 동일 | 동일 |
| DB 연결 실패 | **503** | 동일 | §5 원행 |
| `question` 길이 위반·필수 누락 | **422** | FastAPI 기본 | §5 "성분 합계 ≠ 100%" 와 동일한 Pydantic 검증 |
| 미인증 | **401** | `{"detail":"로그인이 필요합니다"}` | §5 원행 |
| 남의 세션 접근 | **403** | `{"detail":"접근 권한이 없습니다"}` | §5 원행 |
| 세션·메시지 없음 | **404** | `{"detail":"세션을 찾을 수 없습니다"}` | §5.1 리소스 없음 |
| 같은 메시지 재평가 | **409** | — | §5.1 UK 중복 (`uq (message_id, user_id)`) |
| ML 모델 없음 (N4, v1.2) | **404** | `{"detail":"모델을 찾을 수 없습니다"}` | §5 원행 |

> 🔴 **새 오류 코드 0개.** §5 표 6줄 + §5.1 보조 3줄 안에서 전부 해결된다.

### 7.7 RBAC — §3 을 그대로 따르되 예외 2건을 명시한다

#### 예외 1 — `viewer` 가 `POST /agents/*` 를 호출할 수 있다

`api-contract.md` §3.2: `viewer` = **"모든 GET 만. 모든 쓰기 403"**.
그런데 Agent 질의는 **POST 지만 읽기 동작**이다 (`api-contract.md` §8.10 도 "전 역할 R"로 적었다).

| 결정 | `viewer` 에게 `POST /agents/{receiving,shipping,mixing,query,analysis,decision}` 을 **허용**한다 |
|---|---|
| 근거 | 데이터를 변경하지 않는다. `agent_sessions`·`agent_messages`·`agent_runs` 는 **본인 활동 기록**이지 업무 데이터가 아니다 |
| 명시 필요 | §3.2 의 "POST=쓰기" 가정에 대한 **문서화된 예외**다. 구현자가 스스로 판단하게 두면 어긋난다 |
| 예외 아님 | `POST /agents/reindex` 는 **admin 전용**. `POST .../feedback` 은 viewer 허용(본인 평가) |

#### 예외 2 — 🔴 **호출자 권한이 도구 계층까지 전파돼야 한다**

**이것이 Agent 도입의 최대 보안 위험이다.**

> `sales` 사용자가 출하 화면에서 *"공급사별 성분 편차 알려줘"* 라고 물으면,
> Agent 가 **입고 도구를 실행해 제조 데이터를 반환**할 수 있다.
> RBAC 이 라우터에서만 걸리면 **Agent 가 권한 우회 통로가 된다.**

| 통제 | 내용 |
|---|---|
| **T-1 화면 스코프 제한** | `/agents/receiving` 은 **입고 도구 5개만**, `/agents/shipping` 은 **출하 도구 6개만** 노출한다(§3.3.3). 도구 목록은 **엔드포인트가 결정**하고 LLM 이 고르지 않는다 |
| **T-2 역할별 도구 필터** | 스코프 안에서도 역할로 한 번 더 거른다. 원칙: **"그 역할이 화면으로 볼 수 있는 데이터만 도구로도 볼 수 있다"** |
| **T-3 실행 주체** | 도구는 **호출자 JWT 컨텍스트**로 실행한다. 서비스 계정으로 승격 실행하지 않는다 |
| **T-4 감사** | 실행된 도구·인자를 `agent_runs.tool_calls` 에 기록(§6.6). **누가 무엇을 조회했는지 사후 추적 가능** |
| **T-5 금지 목록** | `users`·`audit_logs`·`system_settings`·`ml_models` 는 **어느 역할에도 도구로 노출되지 않는다**(§3.3.1) |

> **전 역할 R** 이 "무엇이든 물어보면 다 보여준다"를 뜻하지 않는다.
> **읽기 권한이 있는 화면의 데이터만** 읽는다.

#### 7.10.1 확증된 충돌

| 실측 | 내용 |
|---|---|
| `frontend/lib/koryo-api.ts:177` | `export const REQUEST_TIMEOUT_MS = 10_000;` — 주석은 *"NFR-P-03 이 배합 최적화에 5초를 허용한다"* |
| `koryo-api.ts:938~968` | **Agent 호출 8개 전부 `timeoutMs` 를 넘기지 않는다** → 기본 10초가 그대로 적용 |
| `koryo-api.ts:264` | 초과 시 문구: `"서버 응답이 없습니다 (POST /agents/receiving — 10초 초과)"` |
| 결과 | **정상 응답(5~20초)이 전부 타임아웃 실패로 그려진다.** 사용자에게는 "AI 가 고장났다"로 보인다 — **실제로는 잘 돌고 있는데** |

> 이건 조용한 실패의 거울상이다. 프로젝트 최대 결함이 "실패를 성공으로 위장"이었다면,
> 이건 **"성공을 실패로 위장"** 이다. 둘 다 화면이 사실과 다른 것을 말한다.

#### 7.10.2 결정 — 서버가 타임아웃의 주인이다

**원칙: 클라이언트 타임아웃은 서버 상한보다 반드시 느슨하다.**
그래야 끊는 주체가 서버가 되고, 사용자는 **의미 있는 상태값**(`timeout` + 근거)을 받는다.
클라이언트가 먼저 끊으면 **연결만 끊길 뿐 아무 정보도 남지 않는다.**

| 계층 | 값 | 근거 |
|---|---|---|
| **SQL 도구 실행** | **3초** (`statement_timeout`) | §3.3.3 |
| **벡터 검색** | **3초** | §3.6 |
| **LLM 1회 호출** | **30초** (`AGENT_LLM_TIMEOUT_S`) | §2.5 |
| **서버 전 구간 상한** | **60초** (재생성 1회 포함) | §5.2.3. 초과 시 `answer_status="timeout"` + 근거 반환 |
| **프론트 (비스트리밍)** | **`AGENT_TIMEOUT_MS = 65_000`** | 서버 60초 + 네트워크 여유 5초 |
| **프론트 (SSE)** | **유휴 15초** — 마지막 이벤트 이후 무응답 15초 | 총시간이 아니라 **유휴**를 잰다 |
| **Nginx** | `proxy_read_timeout 120s` + **`proxy_buffering off`** | §7.10.4 |

#### 7.10.3 프론트 규약 — `timeoutMs: null` 을 쓰지 않는다

| 안 | 판정 |
|---|---|
| ❌ `/data/export` 처럼 `timeoutMs: null` (타임아웃 없음) | **미채택** |
| ✅ **전용 상수 `AGENT_TIMEOUT_MS = 65_000` 을 8개 호출부에 명시** | **채택** |

**`null` 을 쓰지 않는 이유**

| # | 이유 |
|---|---|
| 1 | `/data/export` 는 **파일 다운로드**다. 소요시간이 데이터 크기에 비례하고 브라우저가 진행률을 보여준다. Agent 는 **상한이 존재하는 작업**이고, 상한을 아는 쪽이 안전하다 |
| 2 | **`null` 은 무한 대기다.** 외부 API 나 게이트웨이가 응답 없이 소켓만 붙들면 **스피너가 영원히 돈다.** 그것도 조용한 실패의 한 형태다 |
| 3 | **65초는 "서버가 60초에 끊는다"는 사실을 클라이언트가 아는 형태다.** `null` 은 그 지식을 버린다 |
| 4 | 오류 문구(`koryo-api.ts:264`)가 `(timeoutMs ?? REQUEST_TIMEOUT_MS)/1000` 로 초를 계산한다 → **`null` 이면 "10초 초과"라는 거짓 문구가 나온다** |

**SSE 유휴 타임아웃은 `AbortSignal.timeout()` 으로 구현할 수 없다** (총시간만 잰다).
마지막 이벤트 수신 시각을 기록하고 15초 무이벤트면 `AbortController.abort()` 를 호출하는
**유휴 감시가 별도로 필요하다.** 이 사실을 계약에 명시한다 — 구현자가 `AbortSignal.timeout(65000)` 하나로
끝내면 **정상 스트림이 65초에 끊긴다.**

**응답이 오래 걸린다는 것을 화면이 말해야 한다** (조용한 대기 금지):

| 경과 | 화면 |
|---|---|
| 0~3초 | "근거를 찾는 중…" |
| `sources` 도착 시 | **근거 패널 먼저 표시** (§5.2.2) |
| 3초~ | "답변을 작성하는 중…" |
| 15초~ | "평소보다 오래 걸리고 있습니다" + **취소 버튼** |
| 서버 timeout | `answer_status="timeout"` — **근거는 그대로 두고** "생성 시간 초과" 표시 |

#### 7.10.4 인프라 — Nginx 가 먼저 끊는다

SF-TD2 §1.2 가 **Nginx 리버스 프록시**를 규정했다. **기본값이 Agent 를 깨뜨린다:**

| 설정 | 기본값 | 문제 | 필요값 |
|---|---|---|---|
| `proxy_read_timeout` | **60초** | 서버 상한(60초)과 **정확히 겹친다.** 경계에서 Nginx 가 먼저 끊으면 502 가 나가고 `answer_status` 가 소실된다 | **`120s`** (`/api/v1/agents/` location 한정) |
| `proxy_buffering` | **on** | 🔴 **SSE 가 통째로 버퍼링된다.** 스트리밍이 스트리밍이 아니게 되고 TTFT 이점이 전부 사라진다 | **`off`** |
| `X-Accel-Buffering` | — | 위의 애플리케이션 측 대안 | 응답 헤더에 **`no`** |
| `proxy_http_version` | 1.0 | SSE 에 keep-alive 필요 | **`1.1`** + `proxy_set_header Connection ""` |

> **이 4줄이 없으면 §7.4 스트리밍 설계 전체가 무효다.** `CR-API-001` 승인사항에 포함하고
> SF-TD2 §1.2 개정(`CR-ARCH-001` 영향 범위)에 반영한다.

#### 7.10.5 NFR — Agent 는 기존 성능 게이트 대상이 아니다

> **QA 가 이 문장을 근거로 판정한다. 없으면 Agent 를 NFR-P-01 위반으로 실패 처리한다.**

### 7.11 `sources: string[]` → `Citation[]` 승격 (디자이너 요청 수용)

#### 7.11.1 왜 바꾸는가

`frontend/lib/koryo-api.ts:930` 현행:

```ts
export interface AgentAnswer {
  answer: string;        // ← null 을 표현할 수 없다
  sources: string[];     // ← 화면이 문자열을 파싱해야 한다
  latency_ms?: number;
}
```

| 문제 | 설명 |
|---|---|
| `sources: string[]` | 화면이 문자열에서 테이블명·건수를 **파싱**해야 한다. **그 파싱이 곧 발명이다** — 서버가 말하지 않은 것을 UI 가 만들어낸다 |
| `answer: string` | 🔴 **`null` 을 표현할 수 없다.** `no_evidence`·`rule_violation`·`timeout` 에서 `answer` 는 **null 이어야 한다**(§6.4·§7.5). 현행 타입은 빈 문자열로 위장하도록 강요한다 |
| `latency_ms?` | 낙관적 옵셔널. 실제로는 항상 온다 |

#### 7.11.2 확정 타입

```
AgentAnswerOut
  message_id     bigint
  session_id     bigint
  answer         string | null          ← 🔴 nullable 필수
  answer_status  'ok'|'no_evidence'|'out_of_scope'|'timeout'|'rule_violation'
  sources        Citation[]
  violations     string[]
  partial        boolean
  latency_ms     number
  provider       string | null
  model_id       string | null

Citation
  ord      number
  kind     'data' | 'doc' | 'model'     ← 사용자 어휘. 'sql' 같은 구현 용어를 쓰지 않는다
  label    string                        ← "공급사별 성분 편차 (최근 90일)"
  detail   string | null                 ← "SUP_A·SUP_B·SUP_C, 2026-05-28 ~ 2026-08-26"
  link     string | null                 ← 클릭 가능한 프론트 라우트 (C-2)
  count    number | null                 ← kind='data' 일 때 조회 건수
  snippet  string | null                 ← kind='doc' 일 때 인용 원문 발췌
  score    number | null                 ← kind='doc' 유사도
```

| `kind` | 무엇 | `count` | `snippet` |
|---|---|---|---|
| `data` | 쿼리 카탈로그 실행 결과 (§3.3.3) | **필수** | — |
| `doc` | 벡터 검색 청크 (§3.6) | — | **필수** |
| `model` | ML 예측·최적화 (v1.2, N4) | — | — |

#### 7.11.3 근거의 자격 — 디자이너 요청 2 수용

> **"발췌 없는 문서 근거·건수 없는 데이터 근거는 근거로 세지 않는다."**

**두 곳에서 강제한다:**

| 위치 | 규칙 |
|---|---|
| **N5 collect (§5.2.1)** | `kind='doc'` 인데 `snippet` 이 비었거나, `kind='data'` 인데 `count` 가 `null` 이면 **`Evidence[]` 에 넣지 않는다.** 걸러진 뒤 0건이면 `no_evidence` |
| **V9 (신규 검증, §4.5)** | 응답 직전에 같은 조건을 다시 검사. 위반 시 해당 `Citation` 을 **제거**하고, 남은 근거가 0건이면 **`rule_violation`** |

> **왜 두 번 검사하나**: N5 는 수집 품질, V9 는 **계약 보증**이다.
> 화면은 "`sources` 에 있는 것은 전부 클릭 가능하고 내용이 있다"를 전제로 그린다.
> 그 전제를 서버가 지켜야 UI 가 빈 카드·죽은 링크를 그리지 않는다.

**`count: 0` 은 근거인가** — **그렇다.** "조회했는데 0건"은 **사실이고 유용한 근거**다
("해당 기간 클레임 0건"). 근거가 아닌 것은 **`count` 가 `null` 인 경우** — 조회했는지조차 모르는 것이다.

### 7.12 디자이너에게 회신 — 계약 확정 4건

| # | 디자이너 제기 | 아키텍트 답 |
