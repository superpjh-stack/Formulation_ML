## 계약 범위와의 관계 — 먼저 읽을 것

**본 3건은 계약 범위(화면 42건) 밖이며 별도로 관리한다.** SF-AD1~AD3 · SF-TD1~TD5 본
산출물과 납품용 화면설명서·화면정의서는 42건 기준 그대로이고, 여기에 3건은 실려 있지 않다.

요구사항ID `MES-AD2-063~065`는 **이 문서 묶음에서만 쓰는 번호**다. 본 산출물에 편입할
때는 그 시점의 번호 체계를 다시 확인해야 한다 — 현행 본 산출물에서 063~075는 비기능
요구사항이 쓰고 있다. 기존 001~062는 사업비 산출내역서 FP산정리스트가 참조하므로
건드리지 않는다.

FP 점수는 전부 **산정(안)** 이며, 사업비 산출내역서 반영과 REQ-02(작업지시관리)의 추가
계약 범위는 협의 후 확정한다.

## 신규 테이블 5종

기존 설계에 없어 새로 세운 것들이다. 나머지 참조 테이블은 SF-TD5에 이미 정의돼 있다.

- `RCV_STOCK_THRESHOLDS` (안전재고기준) — 임계재고 경고의 근거. **설계서에 없던 개념**
- `PRC_WORK_ORDERS` / `PRC_WORK_ORDER_TASKS` (작업지시 / 작업지시공정별) — 역할(공정)별 게시의 근거.
  `PROCESS_ID` → `BAS_PROCESSES` 8개 공정, `ASSIGNEE_ID` → `SYS_USERS`. 즉 **역할 = 공정**
- `SHP_DOCUMENTS` / `SHP_DOCUMENT_TEMPLATES` (출고서류발행 / 양식) — 발행이력과 양식을 분리해
  양식이 바뀌어도 과거 발행분이 남는다

## 재생성

`source/`가 유일한 재생성 근거다. 설계 실행본은 계약 범위 42건으로 되돌려 두었기 때문에
신규 3건은 `design.json`에도 `assets/`의 목업 PNG에도 남아 있지 않다.

```
source/ui-spec.json            요구사항·화면·프로그램·테이블이 조인된 상태
source/assets/td3-*.png        목업 3장
```

`tools/`의 스크립트는 **[03 UI Agent] 화면설명서 생성기 안에서 도는 것**이다. 이 저장소에
단독으로 두면 돌지 않는다 — `build_pptx.py`(팔레트·표 헬퍼)와 `build_data.py`에 기대고 있다.
그쪽 `tools/`에 넣고 실행한다.

```
build_addendum.py --restore     보존본 → ui-spec.json (그 뒤 build_pptx.py 로 화면정의서)
build_addendum.py --combine     앱에서 42건과 신규 3건을 나란히 보기
build_addendum_doc.py           상세설명서 HTML
build_addendum_ppt.py           상세설명서 PPT
check_app.py [대상] [--company]  화면설명서 기능테스트 (탭·검색·메뉴이동·키보드 53건)
```

`ui-spec.json`의 `sources.assetsDir`는 작성 시점 기계의 **절대경로**다. 다른 곳에서 다시
만들 때는 이 값을 `source/assets`로 고쳐야 한다.

## 개선업무(AS-IS/TO-BE)의 출처

`source/ui-spec.json`에는 설계 데이터만 있고 개선업무는 없다(SF-TD1 개선업무설계서까지는
손대지 않았다). AS-IS/TO-BE는 킥오프 PPTX 원문을 근거로 `tools/build_addendum_doc.py`의
`IMPROVE` 상수에 적혀 있고, HTML·PPT 두 생성기가 그 하나를 함께 읽는다.
